# Дорожная карта Dahua VTO Access Control

Документ разделяет реализацию и приемку системы на четыре последовательных этапа. Архитектура и действующие контракты описаны в [README.md](README.md).

## Правила выполнения

- Этапы выполняются последовательно; следующий этап начинается после отдельной команды.
- Не используются заглушки, незавершенные функции или скрытые сокращения логики.
- Изменение публичного IPC-, SQL- или Telegram-контракта требует синхронного обновления документации.
- Наличие файла не означает прохождение приемки.
- Реальное реле во время тестов активируется только в контролируемых условиях.
- Секреты, биометрия и реальные видео входов не добавляются в репозиторий.

## Общий статус

| Этап | Результат | Статус кода | Статус приемки |
|---|---|---|---|
| 1 | Конфигурация, SQLite, Dahua API | Файлы созданы | Не завершена |
| 2 | CV-воркер и курьерская автоматизация | Реализован; FPS дискретизируется | Не завершена |
| 3 | QR-генератор и Telegram-бот | Реализованы в коде | Не завершена |

Текущий репозиторий не считается production-ready: отсутствует Этап 4 и полная интеграционная проверка существующего кода.

Порядок работы и правила обновления статусов закреплены в [AGENTS.md](AGENTS.md). Отметка в разделе «Результаты» означает наличие реализации; отметка в разделе «Приемка» — только фактически выполненную проверку.

## Текущие технические несоответствия

Выявлены статическим просмотром кода. Закрытие каждого пункта требует не только изменения кода, но и соответствующей проверки.

- [x] **Нормализация FPS при записи.** Pre-roll, post-roll и live-клип дискретизируются по `RTSP_FPS`. Синтетическая проверка 25 FPS → 10 FPS пройдена; длительность на реальном RTSP остается пунктом аппаратной приемки.
- [x] **Игнорирование служебных и секретных файлов.** `.gitignore` исключает `.env`, виртуальные окружения, `__pycache__/`, базы, WAL и каталог `data/` с медиа.
- [x] **Надежное списание QR через deep link.** Sync/async БД поддерживает защищенный возврат использования; IPC передает `qr_id` и `expected_used_count`. Локально проверены отсутствие присутствия, списание, кулдаун и возврат. Реальная ошибка Dahua остается частью интеграционной приемки.
- [ ] **Постоянный автоматизированный тестовый набор.** Локальные component-проверки выполнены одноразовыми сценариями, но отдельного повторно запускаемого набора тестов пока нет.

- [x] `database.py` с девятью таблицами и индексами.
- [x] Асинхронный доступ через `aiosqlite` для бота.
- [x] Синхронный доступ через `sqlite3` для воркера.
- [x] WAL, `synchronous=NORMAL`, `busy_timeout=5000` на каждом подключении.
- [x] Атомарное списание QR и одноразовое закрытие курьерской сессии.
- [x] `dahua_client.py` с Digest Auth, реле, snapshot и event stream.
- [x] Переподключение event stream и корректная отмена asyncio-задач.

### Приемка конфигурации

- [ ] На целевом Python 3.11+ создается чистое виртуальное окружение и устанавливаются зависимости.
- [ ] Отсутствие обязательной переменной вызывает понятную ошибку с именем переменной.
- [ ] `ADMIN_IDS` принимает список через запятую и отклоняет некорректные значения.
- [ ] Логин и пароль со специальными символами корректно экранируются в RTSP URL.
- [ ] Относительные пути вычисляются от каталога проекта и создаются автоматически.
- [x] Реальный `.env` исключен из Git; правило проверено через `git check-ignore`.

### Приемка SQLite

- [x] Создаются все девять таблиц и синглтон `door_state` с `id=1` — sync/async компонентная проверка.
- [x] На sync и async подключениях подтверждены WAL, NORMAL и timeout 5000 мс.
- [ ] Эмбеддинг `float32[512]` сохраняется и читается как BLOB длиной 2048 байт.
- [ ] Нулевой, не-512-d или содержащий NaN вектор отклоняется.
- [ ] Одноразовый QR успешно списывается один раз; параллельные попытки не удваивают проход.
- [ ] Безлимитный QR не блокируется счетчиком использований.
- [ ] Просроченный, отозванный и исчерпанный QR возвращают различимые причины отказа.
- [ ] Только одна активная курьерская сессия может быть атомарно потреблена.
- [ ] Ошибка открытия не приводит к безвозвратной потере курьерской сессии или QR-использования.
- [ ] Разгрузка может быть включена как после курьерской сессии, так и без нее.
- [ ] Повторный sync/async запуск не приводит к долгим `database is locked` при штатной нагрузке.

### Приемка Dahua API

- [ ] Неверный пароль возвращает управляемую ошибку и не открывает реле повторно.
- [ ] Успешный `openDoor` распознается только при HTTP 200 и корректном ответе устройства.
- [ ] Ответ CGI, отличный от `OK`, считается ошибкой.
- [ ] Snapshot проверяется как непустой JPEG.
- [ ] Multipart-события `BackKeyLight`, `CallNoAnswered`, `VideoMotion` разбираются с `Code`, `action`, `index` и `Data`.
- [ ] Heartbeat не создает ложное событие.
- [ ] Обрыв соединения приводит к переподключению без быстрого цикла перезапросов.
- [ ] Остановка сервиса закрывает HTTP-клиент и не оставляет предупреждения о незакрытых соединениях.

## Этап 2. CV-воркер

### Результаты

- [x] Отдельный `threading.Thread` для RTSP с `grab()`/`retrieve()`.
- [x] Перезапись последнего кадра и кольцевой буфер 3 секунды.
- [x] Post-roll 5 секунд и сборка MP4 через системный `ffmpeg`; кадры дискретизируются по `RTSP_FPS`.
- [x] Live-клип 4 секунды с дискретизацией по `RTSP_FPS`.
- [x] Детектор движения перед тяжелой CV-обработкой.
- [x] InsightFace `buffalo_l` только в процессе воркера.
- [x] Матрица `(N, 512)`, косинусное сходство и кулдауны.
- [x] Обработка `face_tasks` с проверкой одного лица на фотографии.
- [x] ZXing и fallback `cv2.QRCodeDetector`.
- [x] Anti-tailgating по различимым эмбеддингам лиц.
- [x] IPC-команды открытия, live, разгрузки и перезагрузки лиц.
- [x] Outbox-записи для видео, фото и текста.
- [x] Слушатель звонков Dahua.
- [x] Автооткрытие курьеру, память лица на 10 минут и разгрузка.
- [x] Вход курьера по штрихкоду при наличии человека.

### Приемка RTSP и записи

- [ ] Воркер непрерывно работает с реальной панелью не менее 24 часов без роста задержки видео.
- [ ] Последний кадр свежий; сетевой буфер не накапливает секунды отставания.
- [ ] При отключении и восстановлении RTSP захват переподключается без перезапуска сервиса.
- [ ] Каждое успешное открытие создает MP4 длительностью около 8 секунд: 3 до и 5 после.
- [ ] Pre-roll действительно предшествует щелчку реле, а не начинается после него.
- [ ] MP4 открывается в Telegram и стандартных плеерах, имеет `yuv420p` и не содержит аудио.
- [ ] Live-клип содержит свежие 4 секунды, а не старый ring buffer.
- [ ] Нечетные размеры кадра не ломают кодирование.
- [ ] Ошибка или таймаут `ffmpeg` не оставляет заблокированный event loop и зависший процесс.
- [ ] Потребление RAM остается ограниченным при длительной работе и повторных записях.

### Приемка лиц

- [ ] Модель не загружается Telegram-ботом или другими процессами.
- [ ] При статичном кадре InsightFace не вызывается.
- [ ] Зарегистрированный постоялец открывает дверь при сходстве не ниже настроенного порога.
- [ ] Незнакомый человек не открывает дверь.
- [ ] Персональный кулдаун 20 секунд предотвращает повтор одного пользователя.
- [ ] Глобальный кулдаун 8 секунд предотвращает повтор реле для любых методов.
- [ ] Отключение эмбеддинга и `reload_faces` прекращают доступ без перезапуска.
- [ ] Фото без лица, с несколькими лицами и поврежденный файл завершают задачу со статусом `error`.
- [ ] Обработанный временный файл фотографии удаляется.
- [ ] Порог 0.48 проверен на целевой камере днем, ночью и при ИК-подсветке; изменение порога задокументировано.

### Приемка QR и штрихкодов

- [ ] `DOOR:{token}` читается ZXing с требуемого расстояния.
- [ ] OpenCV fallback работает при отключенном результате ZXing.
- [ ] Постоянный QR поддерживает повторные входы.
- [ ] Временный QR отклоняется после `expires_at`.
- [ ] Одноразовый QR нельзя использовать дважды на повторных кадрах.
- [ ] Повторный кадр во время глобального кулдауна не расходует лимит.
- [ ] Ошибка реле не расходует лимит.
- [ ] Посторонний текст QR не вызывает открытие как `DOOR:`.
- [ ] `Code128`, `EAN13`, `DataMatrix` и длинный `QRCode` принимаются только в курьерском сценарии.
- [ ] Штрихкод без человека в свежем кадре не открывает дверь.

### Приемка anti-tailgating

- [ ] Один известный постоялец не создает предупреждение.
- [ ] Известный постоялец и неизвестный человек создают `tailgating_alert=1`.
- [ ] Одно и то же лицо на последовательных кадрах объединяется в одну идентичность.
- [ ] Два известных постояльца не классифицируются как неизвестный проход следом.
- [ ] Видео и предупреждение получают владелец пропуска и `LOG_CHAT_ID`.
- [ ] Запись `access_logs` содержит число обнаруженных людей и путь к видео.
- [ ] Отдельно задокументированы ложные срабатывания и пропуски при закрытых лицах.

### Приемка курьерских сценариев

- [ ] При активной сессии физический звонок и присутствие открывают дверь без Telegram.
- [ ] Сессия закрывается после одного входа и не открывает дверь повторно.
- [ ] Без присутствия автоматического открытия нет.
- [ ] Без активной сессии всем получателям отправляется snapshot и две кнопки.
- [ ] Повторные события одного звонка не создают лавину уведомлений.
- [ ] Курьер узнается повторно в течение 10 минут.
- [ ] После TTL или перезапуска воркера временное лицо не действует.
- [ ] Кнопка разгрузки продлевает автоматические сценарии на 10 минут.
- [ ] Ошибка реле повторно активирует одноразовую сессию и отправляет владельцу ошибку.
- [ ] Новая курьерская сессия сбрасывает предыдущий режим разгрузки пользователя.

### Приемка IPC и отказоустойчивости

- [ ] `unlock_door` создает событие `button` или `qr_deeplink` и post-roll запись.
- [ ] `capture_live_clip` возвращает MP4 в указанный `chat_id`.
- [ ] `enable_unload_mode` работает и после закрытой сессии, и без предшествующей сессии.
- [ ] Некорректный JSON и неизвестный метод не открывают дверь.
- [ ] Ошибка команды возвращается пользователю через outbox; команда не зацикливается.
- [ ] Отмена сервиса завершает RTSP, фоновые записи и HTTP-соединения.

- [ ] `Dockerfile` на Python 3.11+ со всеми системными зависимостями OpenCV, ONNX и ZXing.
- [ ] В образе установлен `ffmpeg` с `libx264`.

- [ ] Временные клипы имеют отдельный каталог и политику очистки.

- [ ] Секреты передаются через `.env`, исключенный из Git.
- [ ] Предусмотрены systemd-юниты как альтернатива Compose.
- [ ] Юниты имеют корректный порядок запуска, restart, пользователя и права на каталоги.
- [ ] Инструкция первого запуска охватывает панель, бота, администратора, зависимости и проверку.

### Приемка развертывания

- [ ] Чистая сборка образа воспроизводима и не требует ручной правки контейнера.
- [ ] Модель InsightFace скачивается/кэшируется контролируемо; отсутствие интернета после подготовки не мешает запуску.
- [ ] После пересоздания контейнеров сохраняются пользователи, QR, лица и журналы.
- [ ] Оба сервиса используют одну базу, но модель загружает только воркер.

- [ ] После `docker compose down` и повторного запуска нет потери постоянных данных.
- [ ] После перезагрузки хоста сервисы восстанавливаются автоматически.
- [ ] Журналы не содержат пароль Dahua, BOT_TOKEN или полные секретные URL.
- [ ] Некорректная конфигурация останавливает сервис с понятной ошибкой.
- [ ] Обновление версии выполняется без удаления volume и с резервной копией SQLite.

### Минимальный сценарий первого запуска

Этот список станет пошаговой инструкцией после фактической проверки deployment-файлов:

1. Назначить панели статический IP и создать отдельную учетную запись.
2. Проверить CGI, RTSP, snapshot и физическое реле штатными средствами.
3. Создать Telegram-бота и определить `BOT_USERNAME`.
4. Получить Telegram ID первого администратора и ID чата журналов.
5. Скопировать `.env.example` в `.env` и заполнить секреты.
6. Установить системный FFmpeg либо собрать Docker-образ.
7. Инициализировать базу и запустить воркер до включения автоматических сценариев.
8. Проверить live-видео без открытия двери.
9. Проверить snapshot и событие звонка.
10. Контролируемо проверить реле и 3+5-секундную запись.
11. Зарегистрировать тестовое лицо и QR, проверить отказ незнакомца и просроченного токена.
12. Проверить курьерские сценарии на тестовой сессии.

## Критерий production readiness

Система готова к эксплуатации только когда:

- завершены результаты всех четырех этапов;
- пройдены критические приемочные сценарии на целевой Dahua VTO;
- подтверждены безопасные пороги лиц и anti-tailgating;
- нет необработанных ошибок и утечек ресурсов при длительном прогоне;
- работают роли, отзыв доступа и защита deep links;
- настроены резервное копирование, хранение/удаление медиа и биометрии;
- проверены восстановление после сбоя, обновление и автозапуск;
- фактические результаты приемки задокументированы отдельно от целевых требований.
