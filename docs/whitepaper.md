# Открытие двери по лицу с потока домофона: whitepaper

Версия 0.1 · 18.11.2026 · Статус: черновик для обсуждения

---

## 1. Резюме

Цель: система, которая принимает видеопоток с камеры домофона, распознаёт зарегистрированного человека и подаёт команду на открытие двери. Всё работает локально, без отправки видео в облако.

Ключевые решения:

| Вопрос | Решение |
|---|---|
| Где работает | Локальный сервер или edge-устройство рядом с домофоном |
| Источник видео | RTSP (H.264/H.265), TCP |
| Распознавание | Детектор лиц + ArcFace-эмбеддинги + косинусное сравнение |
| Анти-спуфинг | Обязательный компонент (liveness), отдельная модель или IR/depth-камера |
| Защита от ошибок | Подтверждение по нескольким кадрам, строгий порог, cooldown |
| Открытие | Абстракция «actuator»: HTTP / MQTT / GPIO / Home Assistant |
| Запасной вход | Ключ или код сохраняется всегда (fail-safe) |

Главный принцип: система открывает дверь, поэтому ошибка «пустили постороннего» (FAR) в разы опаснее ошибки «не узнали своего» (FRR). Все пороги и решения настраиваются в пользу безопасности.

---

## 2. Допущения и границы

**Допущения (требуют проверки):**
- У домофона есть доступный RTSP/ONVIF-поток или можно поставить отдельную IP-камеру.
- Есть способ открыть замок программно (реле, API, HTTP-контроллер).
- В базе от единиц до сотен человек (жилой дом, офис).
- Есть собственные серверы, в том числе с GPU **NVIDIA RTX 3080 (10 ГБ VRAM)**. Инференс работает на нём, отдельное edge-устройство не нужно.
- Сервер и камера/домофон находятся в одной локальной сети (желательно отдельный VLAN).
- Существует рабочая система **tgbot-door** (Dahua VTO + Telegram-бот + CV-воркер на InsightFace; QR, курьерские сессии, журнал входов). Новое решение строится на ней или заменяет её воркер, поэтому требования раздела 6.4 обязательны.

**Вне рамок MVP:** распознавание в толпе, трекинг по нескольким камерам, облачное управление, мобильное приложение для жильцов.

## 3. Требования

### 3.1 Функциональные
1. Принимать RTSP-поток и переподключаться при обрыве.
2. Находить лица в кадре и строить эмбеддинги.
3. Сравнивать с базой зарегистрированных пользователей.
4. Открывать дверь при подтверждённом совпадении.
5. Регистрация и удаление пользователей (по фото).
6. Журнал событий: время, кто, уверенность, исход, снимок отказа (по политике хранения).

### 3.2 Нефункциональные

| Параметр | Цель MVP |
|---|---|
| Задержка «лицо в кадре → команда» | ≤ 1.5 с |
| FAR (ложное открытие) | ≤ 1 на 100 000 попыток (на тестовой выборке) |
| FRR (отказ своему) | ≤ 5–10 % за одну попытку, ≤ 2 % после 3 попыток |
| Доступность | Работа без интернета; автоперезапуск сервиса |
| Приватность | Видео и эмбеддинги не покидают локальную сеть |

Это целевые значения, а не гарантии: реальные цифры определяются только измерением на вашей камере и вашей выборке (раздел 9).

## 4. Архитектура

```
 Камера домофона
   │ RTSP (TCP)
   ▼
┌───────────────┐   последний кадр    ┌──────────────────────────────┐
│ Stream reader │ ──────────────────► │ Pipeline                     │
│ (reconnect)   │                     │  1. Детекция лиц             │
└───────────────┘                     │  2. Фильтры (размер, score)  │
                                      │  3. Liveness                 │
                                      │  4. Эмбеддинг                │
                                      │  5. Поиск по базе            │
                                      └──────────────┬───────────────┘
                                                     │ (имя | None, sim)
                                                     ▼
                                      ┌──────────────────────────────┐
                                      │ Decision engine              │
                                      │  N совпадений за T сек       │
                                      │  cooldown, расписание, ACL   │
                                      └──────┬───────────────┬───────┘
                                             │               │
                                             ▼               ▼
                                      ┌────────────┐   ┌────────────┐
                                      │ Actuator   │   │ Audit log  │
                                      │ HTTP/GPIO/ │   │ + метрики  │
                                      │ MQTT       │   └────────────┘
                                      └────────────┘
```

### Компоненты
- **Stream reader**: отдельный поток, держит только последний кадр (без накопления задержки), TCP-транспорт, автопереподключение, проверка «свежести» кадра.
- **Pipeline**: детекция, выравнивание, эмбеддинг (128/512-мерный вектор), поиск по косинусной близости.
- **Liveness**: отсев фото/экрана/маски (см. раздел 6).
- **Decision engine**: превращает покадровые результаты в решение. Не открывает по одному кадру.
- **Actuator**: изолированный адаптер. Включает таймаут, повтор и подтверждение результата.
- **Audit log**: события и метрики. Хранение по политике.
- **Admin**: CLI для регистрации и удаления, позже веб-панель.

## 5. Технологический стек

### 5.1 Рекомендуемый для MVP

| Слой | Выбор | Комментарий |
|---|---|---|
| Язык пайплайна | Python 3.11+ | Лучшая экосистема ML |
| Видео | OpenCV (FFmpeg backend) или GStreamer | GStreamer лучше для аппаратного декодинга |
| Детекция + эмбеддинг | InsightFace (SCRFD + ArcFace) на ONNX Runtime GPU (CUDA EP) | Высокая точность, быстрый инференс на RTX 3080 |
| Деплой | Docker + NVIDIA Container Toolkit | Фиксируем версии CUDA/cuDNN/onnxruntime-gpu |
| Поиск | NumPy (до тысяч лиц); pgvector/FAISS при росте | Для сотен лиц хватает матричного произведения |
| Хранилище | SQLite → PostgreSQL | Пользователи, события, эмбеддинги |
| Liveness | Отдельная модель (напр. MiniFASNet) или IR/depth | См. раздел 6 |
| Открытие | HTTP / MQTT / GPIO | За интерфейсом actuator |
| Оркестрация | systemd или Docker Compose | Автоперезапуск, healthcheck |
| Наблюдаемость | Структурные логи + Prometheus-метрики | FPS, задержка, число отказов |

### 5.2 Вариант с Go
Если основной бэкенд на Go: Go отвечает за оркестрацию, API, журнал и actuator, а инференс выносится в отдельный сервис (Python или C++ + ONNX Runtime) с gRPC-интерфейсом. Плюсы: чёткое разделение, надёжный долгоживущий процесс. Минусы: второй язык и сетевой хоп.

### 5.3 Железо

**Выбрано: существующий сервер с RTX 3080 (10 ГБ).**

Что это даёт:
- Запас по производительности: `buffalo_l` (SCRFD + ArcFace) занимает порядка 1–2 ГБ VRAM, остаётся место под liveness-модель и несколько потоков. Ожидаемая скорость инференса — десятки кадров в секунду, **точные цифры нужно измерить** на вашей связке.
- Можно использовать более тяжёлые и точные модели, а также ансамбль «эмбеддинг + liveness» без потери задержки.
- Аппаратное декодирование видео (NVDEC) через GStreamer/FFmpeg разгружает CPU при нескольких камерах.
- Один сервер обслуживает несколько дверей.

Что нужно учесть:
- **Единая точка отказа.** Сервер должен быть на ИБП, с автозапуском сервиса и watchdog. Запасной вход обязателен независимо от сервера.
- **Сеть до двери.** Камера, сервер и реле связаны по LAN: нужен отдельный VLAN и мониторинг связи. При потере связи система должна переходить в безопасное состояние (запасной вход), а не открывать дверь.
- **Драйверы и CUDA.** Совместимость версий `onnxruntime-gpu`, CUDA и cuDNN фиксируем в Docker-образе (NVIDIA Container Toolkit).
- **Общий сервер.** Если GPU делится с другими задачами, резервируем VRAM и ставим приоритет, иначе задержка будет скакать.

Ускорение при необходимости: экспорт моделей в TensorRT (через TensorRT Execution Provider в ONNX Runtime) и INT8/FP16. В MVP это не нужно, достаточно CUDA Execution Provider.

Альтернативы на случай, если GPU-сервер не подойдёт для конкретной двери (удалённый объект, нет LAN): Jetson, RK3588 (NPU), Pi + Hailo/Coral. Эти варианты слабее по запасу моделей и сложнее в сборке, в MVP не рассматриваются.

### 5.4 Лицензии моделей (важно!)
Предобученные модели InsightFace распространяются с ограничением для некоммерческого использования. Для коммерческого продукта нужно проверить лицензию, получить разрешение или обучить/взять модель с подходящей лицензией. Это нужно решить до выхода за рамки прототипа.

## 6. Безопасность и анти-спуфинг

### 6.1 Модель угроз

| Атака | Пример | Меры |
|---|---|---|
| Фото | Распечатка или фото на телефоне | Liveness, IR-камера, проверка текстуры/муара |
| Видео | Запись на экране | Liveness, depth, challenge-response (моргание, поворот) |
| Маска / 3D | Силиконовая маска | IR/depth, второй фактор |
| Двойник / похожее лицо | Родственник | Строгий порог, второй фактор для критичных дверей |
| Сетевая атака | Подмена RTSP, прямой вызов реле | Изоляция сети, токены, TLS, VLAN |
| Физическая | Вскрытие устройства | Сервер и реле внутри защищённой зоны |
| Кража базы | Утечка эмбеддингов | Шифрование на диске, права доступа |

### 6.2 Принципы
1. **Лицо не единственный фактор** для критичных дверей: лицо + PIN/телефон/карта.
2. **Fail-safe**: запасной механический или кодовый вход. При отказе системы дверь не должна остаться запертой для эвакуации (требования пожарной безопасности проверять отдельно).
3. **Реле на стороне двери** не должно управляться напрямую из внешней сети.
4. **Токены и TLS** на actuator, доступ только из доверенного сегмента.
5. **Принцип минимальных прав** для файла базы и конфигов.

### 6.3 Liveness: варианты
- **Пассивный (RGB-модель)**: дёшево, но слабее против экранов и качественных масок.
- **Активный (challenge-response)**: просит моргнуть или повернуть голову. Неудобно для домофона, но надёжнее.
- **Аппаратный (IR / структурированный свет / ToF)**: лучшее решение для двери, требует подходящей камеры.

Для MVP без liveness систему нельзя считать защитой. Только демонстрация.

### 6.4 Требования по итогам ревью tgbot-door

Ревью существующего кода (статическое, без запуска) выявило проблемы, которые нужно закрыть до включения входа по лицу на реальной двери. Каждый пункт становится требованием и проверяется на этапе 2.

| # | Находка в текущем коде | Требование |
|---|---|---|
| 1 | Дверь открывается по одному кадру при `similarity ≥ 0.48`, без liveness | Подтверждение N совпадений одного человека за T секунд (стартово 4 за 3 с), порог подбирается по ROC (старт 0.55–0.6), liveness обязателен |
| 2 | Команды `unlock_door` в очереди IPC выполняются после перезапуска воркера сколь угодно поздно | TTL команд 10–15 с: старые команды помечаются обработанными без выполнения. Для QR-команд при этом возвращается использование |
| 3 | QR-токен 32 бита (`token_hex(4)`), эндпоинт различает 404/410/409, лимита запросов нет | Токен ≥ 128 бит (`token_urlsafe(16)`), одинаковый ответ на любые ошибки до проверки присутствия, rate limit по IP |
| 4 | Открытие по `GET /open/...`: превью-боты и сканеры списывают пропуск | GET только показывает страницу, открытие по POST (или только через deep link Telegram) |
| 5 | В курьерской сессии подходит любой длинный штрихкод | Код сверяется с ожидаемым значением (токен сессии или номер заказа) |
| 6 | Курьерский QR по камере не проверяет тип токена и сессию, сессия не закрывается | Единая функция проверки для всех каналов (камера, deep link, HTTP): тип, владелец, активная сессия, закрытие после успеха |
| 7 | Одна ошибка SQLite в `_ipc_loop`/`_face_tasks_loop` останавливает весь воркер | `try/except` с логом и паузой в каждом цикле, запуск под systemd/Docker с `Restart=always`, healthcheck |
| 8 | Outbox: «вечные» ошибки доставки занимают окно из 20 записей и блокируют все уведомления | Статус `failed` после N попыток или сразу при `Forbidden`/`FileNotFound`, выборка по `next_attempt_at` в SQL |
| 9 | Анализ (в том числе чтение QR) отключается, если нет движения | Гейтинг по движению только для лиц и с «хвостом» 2–3 с, штрихкоды читаются независимо |
| 10 | Битый эмбеддинг (`reshape` до проверки размера) роняет `reload_faces` | Валидация длины (`2048` байт) до `reshape`, повреждённая запись пропускается с предупреждением |
| 11 | Кулдаун лица ставится до открытия, при сбое панели человек блокируется на 20 с | Кулдаун ставится только после подтверждённого открытия |
| 12 | Курьерская сессия для кнопки вызова берётся глобально (самая старая), временные лица курьера не сбрасываются при блокировке | Уведомлять владельца сессии и других участников, при блокировке очищать временные лица |
| 13 | Резидент может сам включить лицо, отключённое администратором | Отдельный флаг «отключено админом», недоступный владельцу |
| 14 | Видео входа во временной папке, журнал ссылается на удалённые файлы; таблицы только растут | Постоянное хранилище видео и срок хранения, очистка `ipc_commands`, `bot_outbox`, `access_logs`, `qr_tokens` по расписанию |
| 15 | Инференс на CPU (`onnxruntime`, `ctx_id=-1`) | `onnxruntime-gpu` и `CUDAExecutionProvider` с откатом на CPU и алертом, как в разделе 5.3 |
| 16 | В репозитории `.installer/` (≈71 МБ): `vs_BuildTools.exe`, `link.exe`, `rc.exe`, DLL | Удалить из Git, Build Tools скачивать с сайта Microsoft, добавить в `.gitignore` |
| 17 | `test_bot.py` не запускается (импортирует несуществующие `settings`, `db`) | Автотесты на pytest: атомарность QR, TTL IPC, порог и подтверждение лиц, outbox |

Статус: пункты 1–6 блокируют включение распознавания на реальной двери, остальные нужно закрыть до пилота (этап 3).

## 7. Приватность и правовые вопросы

Биометрические данные считаются особой категорией персональных данных. Во многих юрисдикциях (в том числе в РФ по 152-ФЗ и в ЕС по GDPR) для них нужны явное согласие, цель обработки, срок хранения и защита. Это не юридическая консультация, привлеките юриста до запуска.

Практические меры:
- Письменное согласие каждого зарегистрированного человека, возможность отозвать и удалить данные.
- Хранить **эмбеддинги**, а не фото (но эмбеддинги тоже считаются биометрией).
- Не хранить видео. Снимки отказов хранить ограниченное время или не хранить.
- Шифрование базы, учёт доступа, журнал административных действий.
- Уведомление о видеонаблюдении и обработке биометрии на входе.
- Особая осторожность в общих подъездах: посторонние (в том числе дети) попадают в кадр. Обрабатывайте лица в памяти и не сохраняйте незарегистрированных.

## 8. Основные проблемы и риски

| # | Проблема | Влияние | Решение |
|---|---|---|---|
| 1 | Ракурс, контровой свет, ночь | Падает FRR | Подсветка, IR-камера, WDR, правильная установка (высота ~1.5 м) |
| 2 | Маска, очки, шапка, борода | Падает точность | Регистрация в разных вариантах, несколько фото на человека |
| 3 | Низкое разрешение/сжатие потока | Плохие эмбеддинги | Использовать основной поток, а не sub-stream; минимальный размер лица ≥ 80 px |
| 4 | Задержка потока (буфер RTSP) | Медленная реакция | TCP, только последний кадр, малый GOP, аппаратный декодер |
| 5 | Спуфинг | Взлом | Liveness, IR, второй фактор |
| 6 | Дрейф внешности | Растёт FRR со временем | Дорегистрация, периодическое обновление эмбеддингов |
| 7 | Разные демографические группы | Неравномерная точность моделей | Тестировать на реальной выборке, не доверять публичным бенчмаркам |
| 8 | Ложные срабатывания на похожих | Открытие чужому | Высокий порог, подтверждение по N кадрам, второй фактор |
| 9 | Отказ железа / питания | Дверь не открывается | Запасной вход, watchdog, ИБП |
| 10 | Лицензии моделей | Юридический риск | Проверить до коммерциализации (п. 5.4) |
| 11 | Правовые риски биометрии | Штрафы, претензии | Раздел 7, юрист |
| 12 | Нагрузка при нескольких лицах в кадре | Задержка | Обрабатывать крупнейшее лицо, ограничение FPS |
| 14 | Единая точка отказа (сервер/GPU/сеть) | Дверь не открывается | ИБП, watchdog, автозапуск, запасной вход, мониторинг связи с реле |
| 15 | Конфликт ресурсов GPU с другими задачами | Скачки задержки | Резервирование VRAM, отдельный контейнер/профиль, алерты по задержке |
| 16 | Несовместимость версий CUDA/драйвера/onnxruntime | Падение на старте или откат на CPU | Фиксированный образ, проверка провайдера при старте (лог + алерт, если CUDA недоступна) |
| 13 | Дистанция «лицо при подходе» | Узнаёт слишком рано/поздно | Порог по размеру лица как триггер «человек подошёл» |
| 17 | Устаревшие IPC-команды открытия после перезапуска | Дверь открывается без человека | TTL команд (п. 6.4 № 2) |
| 18 | Слабые QR-токены, GET-открытие, штрихкод без сверки | Несанкционированный вход | п. 6.4 № 3–6 |
| 19 | Падение воркера от одной ошибки БД, блокировка очереди уведомлений | Система «молчит» без видимых ошибок | п. 6.4 № 7–8, supervisor и healthcheck |

## 9. Тестирование и метрики

### 9.1 Метрики
- **FAR**: доля посторонних, которым открыто.
- **FRR**: доля своих, которым отказано.
- **Задержка** от появления лица до команды (p50/p95).
- **FPS** пайплайна, загрузка CPU/GPU.
- **Доступность** (uptime), число переподключений RTSP.

### 9.2 Методика
1. Собрать выборку на реальной камере: свои (разное время суток, ракурсы, очки/шапки) и «чужие» (сотрудники/добровольцы, не зарегистрированные).
2. Построить ROC/DET-кривую по косинусной близости, выбрать порог под целевой FAR.
3. Отдельный набор атак: фото на бумаге, экран телефона, видео. Измерить долю успешных атак (APCER) и ложных отказов живым (BPCER).
4. Нагрузочное тестирование: сутки непрерывной работы, обрывы сети, перезапуск камеры.
5. Регресс при смене модели или порога.

Без измерений на своей выборке любые заявления о точности недостоверны.

## 10. План MVP

### Этап 0: подготовка (2–3 дня)
- Проверить RTSP, разрешение, задержку, ночной режим.
- Определить способ открытия (реле/API), согласовать запасной вход.
- Юридическая проверка и согласия.

### Этап 1: прототип (1 неделя)
- Pipeline из `face_door.py`: RTSP → детекция → эмбеддинг → сравнение.
- Регистрация по фото, логирование, подтверждение по N кадрам.
- Открытие замка в **тестовом режиме** (светодиод/лог, не реальная дверь).
- Критерий готовности: стабильное распознавание 3–5 тестовых людей, задержка ≤ 1.5 с.

### Этап 2: безопасность (1–2 недели)
- Liveness (модель или IR-камера).
- Измерение FAR/FRR и атак, подбор порогов.
- Защита actuator (токен, сеть), шифрование базы.
- Закрыть блокирующие пункты 6.4 (№ 1–6): подтверждение по кадрам, TTL IPC-команд, 128-битные токены, открытие по POST, сверка штрихкодов, единая проверка QR.
- Закрыть пункты надёжности 6.4 (№ 7–11), перейти на CUDA (№ 15), убрать `.installer/` из Git (№ 16), добавить автотесты (№ 17).
- Критерий: целевые FAR/FRR достигнуты на тестовой выборке, атаки фото/экран блокируются, повторный запуск воркера не выполняет старых команд, тесты проходят.

### Этап 3: пилот (2–4 недели)
- Реальная дверь, ограниченная группа, запасной вход всегда доступен.
- Мониторинг, журнал, разбор ложных отказов.
- Сбор отзывов, дорегистрация.
- Критерий: нет ложных открытий, FRR приемлем, система стабильна неделями.

### Этап 4: эксплуатация
- Веб-панель администратора, расписание доступа, уведомления.
- Резервное копирование базы, обновление моделей, алерты.

## 11. Эксплуатация

- **Развёртывание**: Docker Compose или systemd-юнит с автоперезапуском.
- **Мониторинг**: метрики (FPS, задержка, ошибки RTSP, число решений), алерт при отсутствии кадров.
- **Резервное копирование**: зашифрованная копия базы пользователей.
- **Обновления**: сначала на тестовом стенде с регрессионной выборкой, потом на двери.
- **Отзыв доступа**: удаление пользователя должно действовать немедленно (без перезапуска).
- **Журнал**: срок хранения по политике, доступ только администраторам.

## Приложение A. Параметры по умолчанию (стартовые значения)

| Параметр | Значение | Описание |
|---|---|---|
| `threshold` | 0.50 | Косинусная близость; выше = строже. Подбирать по ROC |
| `need` | 4 | Совпадений одного человека в окне |
| `window` | 3.0 с | Окно подтверждения |
| `cooldown` | 10 с | Пауза после открытия |
| `min_face` | 80 px | Минимальная ширина лица |
| `det_score` | 0.60 | Минимальная уверенность детектора |
| `frame_max_age` | 2.0 с | Старше кадр игнорируется |

Все значения стартовые, окончательные определяются измерениями (раздел 9).
