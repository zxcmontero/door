# Эксплуатация

## 1. Healthcheck

### CV-воркер

`ready` только если:

- модели загружены;
- последний кадр не старше 2 секунд;
- event loop и циклы IPC/интерфейсов активны;
- SQLite доступна;
- actuator соответствует выбранному test/Dahua режиму.

`live` означает, что процесс и event loop работают, даже если RTSP временно недоступен. При потере кадров автоматическое открытие запрещено и создается алерт.

### Интерфейсы

- SQLite доступна;
- HTTP server работает;
- outbox цикл активен;
- возраст последней успешной обработки не превышает порог;
- Telegram недоступность переводит уведомления в backoff, но не останавливает локальный доступ.

## 2. Метрики

Prometheus-метрики:

- `door_frame_age_seconds`;
- `door_pipeline_fps`;
- `door_decision_latency_seconds` histogram;
- `door_face_decisions_total{outcome,reason}`;
- `door_liveness_total{outcome}`;
- `door_open_total{method,outcome}`;
- `door_actuator_errors_total`;
- `door_rtsp_reconnects_total`;
- `door_ipc_pending`;
- `door_ipc_oldest_age_seconds`;
- `door_outbox_pending`;
- `door_outbox_failed_total`;
- `door_cpu_fallback_active`;
- процессные CPU/RAM и GPU utilization/VRAM.

Метрики не содержат Telegram ID, токены, имена и биометрию в labels.

## 3. Структурные журналы

Формат JSON: `timestamp`, `level`, `component`, `event`, `door_id`, `command_id`, `outcome`, `reason`, `duration_ms`.

Не записываются токены, пароли, полный RTSP URL, исходные лица, эмбеддинги и необязательные персональные данные. Подробности решения ограничиваются машинной причиной и similarity, если оно разрешено политикой.

Алерты создаются при:

- отсутствии свежего кадра;
- CPU fallback;
- росте p95 выше 1,5 секунды;
- ошибках actuator;
- зависании IPC/outbox;
- повторных SQLite/RTSP reconnect;
- срабатывании watchdog.

## 4. Backup и restore

- SQLite backup выполняется через SQLite backup API или контролируемую остановку, не копированием только основного файла во время записи.
- Копии шифруются и имеют ограниченный срок ротации.
- Доступ к копиям выдается по минимуму.
- Восстановление регулярно проверяется в отдельном окружении.
- Восстановление биометрии учитывает запросы удаления и срок хранения копий.

Минимальная проверка restore: миграции, пользователи, роли, пропуска, аудит, отсутствие секретов в журнале и успешный test actuator.

## 5. Retention

Плановая задача использует параметры из [configuration.md](configuration.md) и правила [database.md](database.md).

- Удаление выполняется пакетами.
- Активные доступы не удаляются по сроку retention.
- Источники фото удаляются после регистрации.
- Удаление биометрии включает активные кандидаты и RAM-лица.
- Видеоархив не создается и не требует очистки.
- Снимки отказов отключены по умолчанию; при включении удаляются по сроку.

## 6. Инциденты

При ложном открытии:

1. Немедленно перевести систему в test actuator или отключить автоматический доступ.
2. Обеспечить работу запасного входа.
3. Сохранить структурированные события без необязательной биометрии.
4. Зафиксировать модель, порог, конфигурацию и условия.
5. Остановить пилот до анализа и повторной приемки.

При потере RTSP, CUDA, SQLite или actuator автоматическое открытие прекращается. Восстановление после сбоя не выполняет просроченные IPC.

## 7. Обновление и отзыв доступа

- Изменения сначала проходят стенд и регрессионную выборку.
- Отзыв QR, `admin_disabled` и блокировка применяются без перезапуска.
- Удаление пользователя очищает его временные курьерские лица.
- Обновление сохраняет БД/volumes и имеет план отката.
- Пилот длится не менее двух недель; ложное открытие означает остановку пилота.
