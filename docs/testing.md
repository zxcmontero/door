# Тестирование и приемка

## 1. Уровни

1. Юнит-тесты чистой логики.
2. Компонентные тесты SQLite, CV, валидатора и outbox.
3. Конкурентные и fault-injection тесты.
4. HTTP/Telegram/IPC интеграционные тесты на doubles.
5. Стендовые тесты RTSP и actuator.
6. Полевая оценка распознавания и атак.
7. Ограниченный пилот.

Тесты изолированы от `.env`, реальной базы, биометрии, Telegram и Dahua. Реальное реле активируется только в отдельной аппаратной группе тестов по явной команде.

## 2. Постоянный pytest-набор

Целевая структура:

```text
tests/
├── unit/
├── component/
├── integration/
├── security/
├── hardware/
└── fixtures/
```

Команды после реализации инфраструктуры:

```bash
python -m pytest tests/unit tests/component tests/security
python -m pytest tests/integration
python -m pytest tests/hardware --run-hardware
```

Hardware-тесты пропускаются без `--run-hardware` и необходимых переменных окружения.

## 3. Обязательные контрактные тесты

### Лицо и liveness

- Один кадр не открывает.
- Три подтверждения не открывают при требуемых четырех.
- Четыре подтверждения разных людей не суммируются.
- Один кадр не дает два голоса.
- Совпадения вне окна удаляются.
- `spoof` сбрасывает кандидата.
- `unknown/error` не дает доступ.
- Поврежденный BLOB не мешает остальным лицам.
- Ошибка actuator не создает cooldown.
- Блокировка и `admin_disabled` действуют немедленно.

### QR и IPC

- Одноразовый QR списывается один раз при параллельных попытках.
- Безлимит не блокируется счетчиком.
- Expired/inactive/exhausted/blocked отклоняются.
- TTL, cooldown и ошибка actuator возвращают использование.
- Перезапуск со старой командой не открывает.
- Idempotency key не создает повторную команду.
- Некорректный JSON не открывает.

### HTTP

- GET не меняет БД и не создает IPC.
- Preview/повторный GET безопасен.
- POST без `confirm=true` отклоняется.
- POST без присутствия получает generic 409.
- Ранние ответы не различают причины токена.
- Повтор idempotency key с тем же fingerprint возвращает идентичные HTTP status и тело без нового списания.
- Повтор ключа с другим fingerprint получает generic 409 без изменения состояния.
- Rate limit и `Retry-After` работают.
- `X-Forwarded-For` учитывается только от доверенного proxy.
- Access logs и ответы не содержат токен.

### Курьеры

- Физический звонок открывает только при одной активной сессии.
- Несколько сессий дают `ambiguous_session` без открытия.
- QR/HTTP используют однозначную session ID.
- Правильный код принимается; неправильный/чужой отклоняется.
- Сессия закрывается один раз после успеха.
- Ошибка actuator сохраняет действующую сессию.
- Блокировка очищает RAM-лица и разгрузку.

### Outbox и надежность

- `sent` только после фактической отправки.
- Forbidden получает `failed` сразу.
- Временная ошибка получает backoff.
- Attempts/next_attempt_at сохраняются после перезапуска.
- Двадцать отложенных записей не блокируют новую.
- Ошибка SQLite в одном цикле не останавливает остальные.
- Отмена сервиса не подавляется.

## 4. FAR/FRR

Определения:

- FAR = ложные открытия посторонних / все попытки посторонних.
- FRR = отказы зарегистрированным / все попытки зарегистрированных.

Для каждой попытки сохраняются анонимизированный subject ID, условия, результат, similarity, liveness и версия модели. Независимость повторных кадров одного подхода определяется методикой: кадры одного подхода не считаются независимыми попытками.

Цели:

- FAR не более 1/100000;
- FRR не более 5–10% за попытку и не более 2% после трех попыток.

Для доказательства верхней границы 1/100000 с доверием 95% при нуле ложных открытий используется не менее примерно 299 573 независимых попыток посторонних («правило трех»: `3 / 0.00001`). Меньшая выборка дает только наблюдаемую оценку и не доказывает целевую границу.

## 5. Liveness

Отдельные наборы:

- печатная фотография;
- экран телефона;
- видеозапись;
- разные расстояния и яркость экрана;
- живые люди в тех же условиях.

Измеряются APCER (успешные атаки) и BPCER (ложные отказы живых). Порог фиксируется вместе с моделью. Маски/3D требуют отдельной оценки, если заявлена защита от них.

## 6. Аппаратная приемка

- RTSP не менее 24 часов без роста задержки/RAM.
- Обрыв и восстановление RTSP/HTTP/SQLite.
- Проверка свежести последнего кадра.
- p50/p95 задержки и FPS на CUDA и CPU fallback.
- Контролируемое открытие реле с TTL 5 секунд.
- День, ночь, ИК, контровой свет, очки/шапки и разные ракуры.
- Потеря питания/сервера с доступным запасным входом.
- Отсутствие исходящих кадров, видео и биометрии в local-only режиме.

## 7. Пилот

Пилот длится не менее двух недель после успешной стендовой приемки. Критерий — ноль ложных открытий и приемлемый FRR на согласованной выборке. Любое ложное открытие останавливает пилот, фиксируется как инцидент и требует повторной приемки после исправления.
