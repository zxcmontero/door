# Контракты доступа

## 1. Токены и QR

- Секрет: `secrets.token_urlsafe(16)`, не менее 128 бит энтропии.
- Внешний формат: `v1_{secret}`.
- В SQLite сохраняется только SHA-256 hash полного токена; исходный токен существует в выданном QR/ссылке.
- QR payload по умолчанию: `DOOR:v1_{secret}`.
- HTTP payload: `{PUBLIC_BASE_URL}/open/{kind}/v1_{secret}`.
- `kind`: `qr` для обычного пропуска, `cour` для курьерского.
- Telegram deep link: `https://t.me/{BOT_USERNAME}?start={kind}_v1_{secret}`.
- `max_uses=0` означает безлимит; `expires_at=NULL` — отсутствие срока.

Токен не попадает в приложение/Proxy access logs в открытом виде. Для URL применяются `Cache-Control: no-store` и `Referrer-Policy: no-referrer`.

## 2. Присутствие

Стартовые значения:

- лицо в свежем кадре: не более 5 секунд назад;
- движение: не более 4 секунд назад;
- физический звонок курьера: лицо или движение не более 3 секунд назад;
- отсутствие свежего RTSP: дистанционное открытие запрещено.

Присутствие не заменяет авторизацию пропуска и не доказывает живость владельца. Для QR оно является дополнительной защитой от удаленного/случайного открытия.

## 3. Общий результат валидатора

```python
@dataclass(frozen=True)
class AccessDecision:
    allowed: bool
    reason: str
    qr_id: int | None
    owner_id: int | None
    expected_used_count: int | None
    courier_session_id: int | None
```

Внутренние причины: `ok`, `invalid`, `inactive`, `expired`, `exhausted`, `blocked`, `no_presence`, `no_session`, `ambiguous_session`, `wrong_code`, `cooldown`, `stale_command`, `actuator_error`.

HTTP не раскрывает внутреннюю причину до подтверждения присутствия. Подробный результат доступен только в защищенном аудите.

## 4. HTTP API

### GET `/open/{kind}/{token}`

- Возвращает HTML-подтверждение.
- Не обращается к actuator и не создает IPC.
- Не меняет счетчики, сессии и статусы.
- Не раскрывает существование и состояние токена.
- Не содержит внешних ресурсов, которым мог бы передаваться Referer.

### POST `/open/{kind}/{token}`

Заголовки:

```text
Content-Type: application/json
Idempotency-Key: {unique_value}
```

Тело:

```json
{"confirm": true}
```

- Операция выполняется только при `confirm=true`, свежем присутствии и успешной валидации.
- Повтор с тем же `Idempotency-Key` и тем же `request_fingerprint` возвращает сохраненные HTTP status и тело без нового списания/IPC. Хранение определено в [database.md](database.md).
- Повтор ключа с другим fingerprint получает generic `409 Conflict` без изменения состояния.
- Cookie-аутентификация и cross-origin разрешения не используются.
- Успешная постановка команды: `202` с generic message.
- Нет присутствия: `409` с одинаковым сообщением независимо от состояния токена.
- Недействительный доступ после присутствия: единый `410` без внутренней причины.
- Rate limit: `429` с `Retry-After`.

Стартовый rate limit: 10 POST в минуту и 30 GET в минуту на IP, блокировка 60 секунд после превышения. Значения проверяются на стенде. Доверенные proxy перечисляются явно; `X-Forwarded-For` принимается только от них.

## 5. Telegram

Deep links используют общий валидатор. Повторная кнопка повторяет весь процесс, включая присутствие и атомарное списание. Гостевая ссылка не дает постоянного или административного управления. `blocked` отклоняется на каждом входе.

Telegram передает только необходимый текст и клавиатуры. Фото, видео, исходные изображения лиц и эмбеддинги не отправляются.

## 6. IPC

Команда `unlock_door`:

```json
{
  "user_id": 123,
  "chat_id": 456,
  "method": "qr_deeplink",
  "details": "guest pass",
  "qr_id": 42,
  "expected_used_count": 1,
  "courier_session_id": 7,
  "idempotency_key": "optional-http-key"
}
```

- `created_at` и `expires_at` хранятся как Unix timestamp `REAL`.
- TTL: 15 секунд по умолчанию, допустимый диапазон 10–15.
- Просроченная команда получает `processed` с `result=stale`, actuator не вызывается.
- Для QR выполняется возврат по `qr_id` и `expected_used_count`.
- Команда имеет уникальный `idempotency_key`, если создана через HTTP.
- `chat_id` используется только для текстового результата.

Методы аудита: `face`, `qr_camera`, `qr_deeplink`, `button`, `courier_auto`, `courier_barcode`.

## 7. Курьерская state machine

```text
ACTIVE
  ├─ истек срок → EXPIRED
  ├─ блокировка владельца → CANCELLED
  ├─ ambiguous physical ring → ACTIVE + notifications
  ├─ actuator error → ACTIVE, если срок не истек
  └─ actuator success → CONSUMED
                         ├─ temporary face RAM TTL 600 с
                         └─ UNLOAD optional
```

### Выбор сессии

- QR/HTTP содержит `courier_session_id`, поэтому сессия однозначна.
- Физический звонок автоматически открывает только при ровно одной активной сессии на панель.
- При нескольких активных сессиях физический звонок не открывает: владельцы и участники получают `ambiguous_session`.
- При отсутствии сессии выполняется обычное текстовое уведомление участников.

### Ожидаемый код

Постоялец задает код заказа при создании сессии. В БД хранится SHA-256 hash кода с session salt. Code128, EAN13, DataMatrix и QRCode принимаются только при совпадении, свежем присутствии и активной сессии. Длина кода не имеет авторизационного значения.

### Временное лицо и разгрузка

- Временное лицо хранится только в RAM с TTL 600 секунд.
- Повторное распознавание продлевает TTL только после успешного открытия.
- Разгрузка длится 600 секунд и использует те же проверки кода/присутствия.
- Блокировка владельца очищает временные лица и отменяет разгрузку.

## 8. Атомарность и возвраты

- Списание QR и закрытие сессии выполняются через `BEGIN IMMEDIATE`.
- До успеха actuator счетчик возвращается условным `UPDATE ... WHERE used_count = expected_used_count`.
- При TTL, cooldown, ошибке IPC/actuator доступ не расходуется.
- При успехе одноразовая сессия закрывается в той же логической операции фиксации результата.
