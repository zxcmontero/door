# Безопасность

## 1. Приоритет

Главный риск — ложное открытие постороннему. Любая неопределенность в CV, liveness, присутствии, IPC или actuator завершается отказом, а не открытием.

## 2. Модель угроз

| Угроза | Обязательные меры |
|---|---|
| Фото/экран/видео | Liveness, набор атак, APCER/BPCER |
| Маска/3D | IR/depth или второй фактор для критичных дверей |
| Похожий человек | ROC/DET, N/T, строгий порог, второй фактор при необходимости |
| Подмена RTSP/вызов реле | LAN/VLAN, ограничение сети, защищенная физическая зона |
| Перебор токена | 128 бит, rate limit, одинаковые ранние ответы |
| Preview-бот | GET без side effects, явный POST |
| Старая команда | IPC TTL и проверка перед actuator |
| Произвольный штрихкод | Сверка с ожидаемым кодом сессии |
| Кража базы | Hash токенов, шифрование, минимальные права |
| Утечка через логи | Redaction URL, токенов, секретов и биометрии |
| Отказ сервера/сети | Запасной вход, ИБП, watchdog, healthcheck |
| Физический доступ | Сервер и реле в защищенной зоне |

## 3. Liveness

MVP использует отдельную liveness-модель на том же GPU. Выбор конкретной модели фиксируется перед этапом 1 после проверки лицензии и набора атак. IR/depth/ToF остается предпочтительным аппаратным усилением для критичных объектов.

Состояния:

- `live` — кандидат допускается к сравнению;
- `spoof` — кандидат сбрасывается, создается отказ;
- `unknown/error` — кандидат не получает подтверждение, открытие запрещено.

Каждое подтверждение N/T проходит liveness. Один кадр не дает больше одного голоса на человека.

## 4. Decision engine

- Стартовое правило: 4 подтверждения одного `user_id` за 3 секунды.
- Подтверждения необязательно идут подряд, но относятся к разным кадрам внутри окна.
- `spoof` сбрасывает соответствующего кандидата.
- `unknown/error` не дает голоса; результаты старше окна удаляются.
- Результаты разных людей не суммируются.
- Порог выбирается по ROC/DET и хранится с версией модели и выборки.
- Стартовые фильтры: ширина лица 80 px, `det_score=0.60`.
- Cooldown 10 секунд устанавливается только после успеха actuator.

Расписания и ACL входят в decision engine: правило содержит пользователя, дверь, метод, интервалы времени и административный запрет. Отсутствие разрешающего правила означает отказ.

## 5. Присутствие

Присутствие проверяется непосредственно перед созданием команды и повторно воркером перед actuator.

- Для QR/HTTP: лицо ≤5 с или движение ≤4 с.
- Для физического курьерского звонка: лицо/движение ≤3 с.
- Для лица: только свежий кадр ≤2 с и завершенное N/T + liveness.
- Нет свежего RTSP — автоматического открытия нет.

Присутствие не заменяет токен, роль или ожидаемый код.

## 6. Секреты и журналы

- `.env`, пароли, BOT_TOKEN, полный RTSP URL и токены не выводятся в логи.
- В SQLite хранятся hash токенов и ожидаемых кодов.
- Reverse proxy маскирует `/open/...` path/query в access logs.
- HTTP ответы используют `Cache-Control: no-store` и `Referrer-Policy: no-referrer`.
- Ошибки actuator не содержат credentials или секретный URL.
- Структурные логи имеют поля `timestamp`, `level`, `component`, `event`, `door_id`, `command_id`, `outcome`, `reason`; секретные payload не записываются.

## 7. Роли и отзыв

- Каждый вход в обработчик проверяет роль на сервере.
- `admin_disabled` не снимается постояльцем.
- Блокировка отключает QR, лица, кандидаты, курьерские сессии и временные RAM-лица.
- Удаление биометрии включает векторы и исходные изображения.
- Изменения доступа записываются в admin audit без лишних персональных данных.

## 8. Сеть и оборудование

- Панель, воркер и actuator находятся в выделенном VLAN.
- Прямой доступ к реле из внешней сети запрещен.
- Внешние actuator API используют токены и TLS.
- Dahua HTTP без TLS ограничен изолированным сегментом.
- Сервер и реле находятся в защищенной физической зоне.
- GPU-инференс выполняется на RTX 3080; CPU fallback вызывает алерт.
- Механический/кодовый запасной вход не зависит от системы.
