# Руководство по постановке задач

Документ связывает каждую задачу с обязательными источниками, результатом и проверками. Используйте идентификатор задачи в запросе, чтобы не повторять все требования и не давать исполнителю выбирать архитектуру самостоятельно.

## 1. Как дать задачу

Короткий формат:

```text
Выполни T2.3 по docs/task-guide.md в коде.
Сначала прочти AGENTS.md, ROADMAP.md и документы, обязательные для T2.3.
Соблюдай стандартные ограничения и критерии из руководства.
Следующую задачу не начинай.
```

Если нужны дополнительные ограничения, добавляйте их отдельно:

```text
Дополнительно: реальную панель не использовать, новые зависимости не добавлять.
```

Если запрос противоречит профильной спецификации, исполнитель обязан указать противоречие и остановиться до уточнения, а не молча выбрать вариант.

## 2. Обязательное начало каждой задачи

Исполнитель должен:

1. Прочитать `AGENTS.md`, актуальную часть `ROADMAP.md` и документы из строки задачи.
2. Проверить `git status` и не перезаписывать чужие изменения.
3. Прочитать только затронутый код и существующие тесты.
4. Подтвердить, что контракт понятен и однозначен.
5. При противоречии или отсутствии критического решения остановиться с конкретным вопросом.
6. Не считать существующий код источником новых требований.

## 3. Стандартные ограничения

Они действуют для всех задач, если пользователь явно не изменил их:

- Реальное реле не активировать.
- `.env`, реальную базу, биометрию и журналы не читать.
- Использовать временные SQLite, синтетические кадры и test doubles.
- Новые зависимости не добавлять без согласования.
- Не создавать видеоархив и не передавать медиа/биометрию внешним сервисам.
- Не менять соседние контракты вне строки задачи.
- Не оставлять заглушки и частичную реализацию.
- Добавить постоянные pytest-тесты, включая негативный сценарий.
- Обновить профильную документацию и ROADMAP без неподтвержденных отметок приемки.
- Не переходить к следующей задаче без отдельной команды.

## 8. Обязательный результат исполнителя

В конце задачи исполнитель сообщает:

- реализованный результат;
- измененные файлы;
- добавленные постоянные тесты;
- выполненные команды и их фактический результат;
- что проверено на doubles, а что на оборудовании;
- обновленные документы;
- оставшиеся ограничения;
- статус ROADMAP без неподтвержденных отметок.

Импорт, AST, mock и одноразовый скрипт не называются аппаратной приемкой. Если проверка невозможна, задача не отмечается как полностью принятая.

## 9. Поддержание руководства

При появлении нового типа работы сначала добавьте строку с новым ID, документами и проверкой. Статусы хранятся только в `ROADMAP.md`; это руководство не дублирует их.
