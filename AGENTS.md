# Руководство по разработке Dahua VTO Access Control

Этот файл задает рабочие правила для последующих этапов. Он предназначен для разработчиков и AI-агентов, которые продолжают проект без исходного контекста.

## Источники истины

- `README.md` — целевая архитектура, конфигурация, IPC и действующие контракты.
- `ROADMAP.md` — состав этапов, критерии приемки, известные несоответствия и фактический статус.
- `AGENTS.md` — порядок разработки, границы модулей и правила завершения работы.
- Код — фактическое поведение системы. Если код и документация расходятся, это расхождение нужно устранить или явно зафиксировать в `ROADMAP.md`, а не скрывать.

Перед изменениями прочитать эти документы и проверить `git status`. Не перезаписывать чужие или не связанные с задачей изменения.

## Последовательность этапов

1. Конфигурация, SQLite и Dahua API.
2. CV-воркер, видеозаписи, лица, коды и курьерская автоматизация.
3. `qr_generator.py` и Telegram-бот.
4. Docker, systemd и проверенная инструкция первого запуска.

Следующий этап начинается только по отдельной команде пользователя. Наличие файла позволяет отметить результат как написанный, но не как принятый. Приемочный пункт отмечается только после воспроизводимой проверки.

Текущее состояние: код Этапов 1–3 создан, Этап 4 не начат, интеграционная приемка не завершена. Актуальные несоответствия перечислены в `ROADMAP.md`.

## Обязательные правила реализации

- Не оставлять `# TODO`, `pass`, `...`, незаполненные обработчики и сокращенную логику.
- Не выдавать статический анализ за интеграционную проверку.
- Не называть проект production-ready, пока не выполнены критерии `ROADMAP.md`.
- Поддерживать Python 3.11+ и версии зависимостей из `requirements.txt`.
- Использовать aiogram 3.x: `Router`, фильтры `F`, `StatesGroup`, builders и типы входных файлов из исходных требований.
- Не добавлять зависимости без необходимости; сначала проверить существующий стек.
- При изменении SQL, IPC, callback-data, конфигурации или пользовательского сценария синхронно обновить документацию.
- После изменения поведения проверить и актуализировать комментарии и docstring, описывающие старое поведение.

## Границы процессов

### `cv_worker.py`

Только этот процесс:

- загружает InsightFace;
- читает RTSP и анализирует кадры;
- поддерживает матрицу эмбеддингов и временную память курьеров;
- обрабатывает Dahua events;
- координирует открытие реле, глобальный кулдаун и post-roll записи.

Воркер запускается в одном экземпляре на панель и базу. Блокирующие операции OpenCV, SQLite, FFmpeg и файлового ввода-вывода не должны блокировать asyncio event loop; для них используется существующий подход через `asyncio.to_thread` или отдельный поток.

### `bot.py`

Telegram-процесс и необязательный HTTP endpoint для QR-ссылок:

- использует `aiosqlite`, но не загружает CV-модели;
- проверяет роли на каждом входе в обработчик;
- создает IPC-команды и обрабатывает `bot_outbox`;
- не обходит воркер для автоматического открытия, чтобы не нарушить единый кулдаун и запись входа.

### `database.py`

SQLite одновременно является базой и IPC-транспортом. Каждое новое подключение обязано выполнить:

```sql
PRAGMA journal_mode=WAL;
PRAGMA synchronous=NORMAL;
PRAGMA busy_timeout=5000;
```

Операции списания QR и потребления курьерской сессии должны оставаться атомарными через `BEGIN IMMEDIATE`. Нельзя разносить проверку и изменение лимита по разным транзакциям.

## Инварианты предметной области

- Время в SQLite — Unix timestamp `time.time()` как `REAL`.
- Для интервалов и TTL внутри одного процесса используется `time.monotonic()`; монотонные значения нельзя сохранять или сравнивать с Unix timestamps.
- Эмбеддинг — ненулевой конечный `float32[512]`, BLOB длиной 2048 байт. Для сравнения векторы нормализуются.
- Глобальный кулдаун реле — 8 секунд для всех методов, персональный кулдаун лица — 20 секунд.
- `max_uses=0` означает безлимитный QR; `expires_at=NULL` — отсутствие срока действия.
- Повторные кадры, глобальный кулдаун и ошибка реле не должны расходовать одноразовый QR.
- Курьерская сессия потребляется один раз. При ошибке открытия она восстанавливается, если еще действует.
- Временные лица курьеров существуют только в RAM и исчезают после перезапуска.
- Один медиафайл outbox удаляется только после обработки всех связанных получателей.
- Все успешные открытия создают журнал и запись входа; ошибка кодирования видео не должна отменять журналирование факта открытия.

## Безопасность

- Не читать, не выводить и не коммитить `.env`, реальные токены, пароли, RTSP URL с учетными данными, биометрию и реальные записи входов.
- `BOT_TOKEN`, пароль Dahua и полный RTSP URL не должны попадать в логи и сообщения об ошибках.
- Незарегистрированный и `blocked` пользователь не получает управление дверью. Проверка прав обязательна для Reply, Inline, callback, deep link, FSM и административных действий независимо от видимости кнопок.
- Постоялец изменяет только свои QR и может переключать существующие лица; регистрация новых лиц требует серверной проверки роли `admin`. Административные операции требуют серверной проверки роли `admin`.
- QR и курьерские deep links проверяют активность, срок, лимит и присутствие. Callback с повтором выполняет новую проверку, а не использует старый результат.
- Реальное реле активируется только по явной задаче и в контролируемых условиях.

## Контракты Telegram и IPC

- Формат QR по умолчанию: `DOOR:{token}`; при заданном `PUBLIC_BASE_URL`: `{PUBLIC_BASE_URL}/open/{kind}/{token}`. В обоих случаях `border=4`, внешняя рамка 40 px `#222222`.
- Deep links: `qr_{token}` и `cour_{token}`; HTTP endpoint: `/open/{kind}/{token}` с тем же контрактом списания.
- Существующие callback-data: `unlock_door`, `unlock_unload:10`, `courier_unload:10`.
- QR deep link использует контракт из `README.md`: атомарное списание, передача данных для возврата использования и возврат при любом неуспешном открытии.
- Outbox получает `status='sent'` только после фактической отправки. Временная ошибка оставляет запись доступной для повтора; постоянная ошибка не должна остановить весь dispatcher.

## Проверка и завершение изменения

Перед завершением:

1. Проверить сценарий пользователя, а не только импорт или компиляцию.
2. Выполнить доступные проверки затронутого уровня: статические, компонентные, интеграционные или аппаратные.
3. Явно перечислить проверки, которые невозможно выполнить без Dahua, Telegram или целевого окружения.
4. Проверить `git status`, удалить созданные проверками ненужные артефакты и не трогать чужие файлы.
5. Обновить `ROADMAP.md`: отдельно указать написанный код и фактически пройденную приемку.
6. В итоговом сообщении назвать измененные файлы, результаты проверок и оставшиеся ограничения.

Нельзя отмечать работу завершенной, если затронутый сценарий не работает, проверки завершились ошибкой или реализация частична.
